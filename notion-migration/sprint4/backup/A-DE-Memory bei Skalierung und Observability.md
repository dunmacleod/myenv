# Memory bei Skalierung und Observability

Notion page: https://app.notion.com/p/Memory-bei-Skalierung-und-Observability-0949418319f382e89d430172db6bb16a
Backed up before n8n migration

Vela Systems betreibt sein internes Multi-Agent-Tooling seit einigen Wochen. In einem Single-Session-Test mit einem Agenten und einem Nutzer funktionierte alles. Die Memory-Boundary-Entscheidungen hielten. Die State-Handoffs wurden sauber abgeschlossen. State erholte sich korrekt, wenn die Session unterbrochen wurde. Jetzt will das Vela-Team das System für die gesamte Customer-Operations-Gruppe öffnen: dreißig Nutzer in zwei Teams, die gleichzeitig Anfragen über die drei Spezialagenten laufen lassen. Ob es grundsätzlich funktioniert, ist geklärt. Die eigentliche Frage lautet jetzt: Funktioniert es auch bei Skalierung, und merkst du, wenn es das nicht tut?
Diese Lektion behandelt beide Hälften dieser Frage. Die erste Hälfte dreht sich darum, wie sich Memory und State anders verhalten, wenn das System unter Last von mehreren gleichzeitigen Nutzern steht. Die zweite Hälfte dreht sich um Observability, konkret darum, was geloggt werden sollte, damit du einen Fehler nachvollziehen kannst, statt ihn zu erraten, wenn in einem Multi-Agent-System etwas schiefgeht.
> 💡 In dieser Lektion lernst du, wie sich Memory und State unter gleichzeitiger Last verhalten und was du für Observability in einem Multi-Agent-System loggen solltest.
## Wie Skalierung das Memory-Bild verändert
Wenn ein Nutzer eine Anfrage ausführt, wirken Memory-Grenzen sauber und selbstverständlich. Das Kontextfenster gehört zur Session. Flow-State-Schlüssel aktualisieren sich in einer klaren Sequenz. Nichts konkurriert um Schreibzugriff.
Wenn dreißig Nutzer gleichzeitig Anfragen ausführen (einige beim Classifier, einige mitten im Handoff zu einem Spezialisten, einige warten auf die Antwort eines zweiten Agenten), wird das Bild auf zwei konkrete Arten komplizierter.
Kontextfenster skalieren sauber. Flow State nicht.
Jede Nutzer-Session erhält sein eigenes Kontextfenster. Es gibt kein Teilen, keine Konkurrenz, keine Cross-Contamination. Die Architektur isoliert Sessions bereits per Design, daher ist Concurrency auf Kontextfenster-Ebene kein Problem.
Flow State ist anders. Wenn deine Agenten in einen geteilten Flow-State-Schlüssel schreiben (einen Schlüssel, der nicht pro Session gescoped ist), dann schreiben dreißig gleichzeitige Sessions in denselben Ort. Der letzte Schreibvorgang gewinnt. Frühere Schreibvorgänge werden still überschrieben. Das ist kein Bug, den du im Testing sehen wirst; er zeigt sich erst, wenn zwei Sessions genau im selben Moment mitten in der Ausführung sind.
Der Fix ist dasselbe Prinzip aus Sprint 3: Schreib-Ownership pro Schlüssel, pro Session gescoped. Jeder Schlüssel, der nutzerspezifischen Kontext trägt, muss per Session-Identifier namespaced sein, nicht global geschrieben werden. Das ist eine Produktionskonsequenz der Memory-Boundary-Entscheidungen, die du bereits getroffen hast.
Persistent-Store-Lesezugriffe sammeln sich an.
In einem Single-Session-System ist ein Lookup in einen persistenten Store (eine Qdrant-Collection, eine Airtable-Base, eine externe API) ein Aufruf pro Anfrage. In einem System mit dreißig gleichzeitigen Nutzern vervielfachen sich diese Aufrufe. Das gesamte Lookup-Volumen wird dadurch bestimmt, wie viele Agenten Lesezugriffe ausführen und wie viele Sessions gleichzeitig laufen.
Systeme, die im Testing einen Persistent-Store-Aufruf pro Anfrage ausgeführt haben, können in der Produktion bei Spitzenlast dreißig ausführen. Das ist ein Grund, bewusst zu entscheiden, welcher Agent sie ausführt und ob ein Ergebnis in Flow State weitergetragen werden kann, statt von jedem Agenten in der Kette erneut abgerufen zu werden.
## Was Observability für ein Multi-Agent-System bedeutet
Observability bedeutet, die richtigen Dinge an den richtigen Stellen zu loggen, damit du in den Logs lesen und identifizieren kannst, wo der Fehler passiert ist, wenn das System sich unerwartet verhält (ein Agent gibt veraltete Ausgabe zurück, ein Handoff wird abgeschlossen, trägt aber den falschen State, eine Session erholt sich in den falschen sicheren State), ohne die Session von Grund auf reproduzieren zu müssen.
In einem Single-Agent-System ist die Fehlerverfolgung relativ simpel: Der Agent hat seine Aufgabe entweder erledigt oder nicht, und das Ergebnis dient als direkter Beleg. In einem Multi-Agent-System hingegen können Fehler an diversen Entscheidungspunkten auftreten: im Classifier, bei den Handoff-Regeln zwischen den Agenten, beim State-Schreibvorgang eines Spezialisten oder in der Recovery-Logik nach einer Unterbrechung. Ohne entsprechendes Logging weißt du am Ende nur, dass die Ausgabe fehlerhaft ist. Protokollierst du jedoch die relevanten Daten, lässt sich jeder Fehler vom Output lückenlos bis zu dem spezifischen Agenten und exakt der Entscheidung zurückverfolgen, die ihn verursacht haben.
## Die vier Positionen, die geloggt werden sollten
Für ein Multi-Agent-System in Agentflow V2 entsteht Observability-Abdeckung durch Logging an vier Positionen. Jede Position entspricht einer Entscheidung, die das System trifft und die ohne Logeintrag unsichtbar ist.
- Position 1: Anfrage empfangen und klassifiziert
  - Log: die rohe Eingabe, der query_typeWert, der in Flow State geschrieben wurde, und der Session-Identifier. Das ist die erste Entscheidung, die das System trifft. Wenn die Ausgabe der gesamten Kette falsch ist, zeigt dir dieser Logeintrag, ob der Classifier die richtige Entscheidung getroffen hat, bevor irgendetwas anderes lief.
  - Was loggen: { session_id, timestamp, raw_query, query_type_written }
- Position 2: State vor dem Handoff geschrieben
  - Log: jeden Flow-State-Schlüssel, den der Classifier oder Koordinator schreibt, bevor die Kontrolle an einen Spezialisten übergeht. Das ist der Handoff-Vertrag, also eine Menge von Werten, die der empfangende Agent lesen wird. Wenn der Spezialist später veraltete oder falsche Ausgabe zurückgibt, zeigt dir dieser Logeintrag, ob die Eingabe, die er erhalten hat, korrekt war.
  - Was loggen: { session_id, timestamp, handoff_state_snapshot }
- Position 3: State beim Eintritt des Spezialisten gelesen
  - Log: die Flow-State-Werte, die der Spezialist in dem Moment liest, in dem er mit der Ausführung beginnt. Das ist die empfangende Seite des Handoffs. Der Vergleich der Logs aus Position 2 und Position 3 für dieselbe Session zeigt dir, ob der Handoff-Vertrag intakt angekommen ist.
  - Was loggen: { session_id, timestamp, agent_id, state_read_on_entry }
- Position 4: Antwort geschrieben
  - Log: die Ausgabe, die der Agent schreibt, zusammen mit dem Session-Identifier und einem Completion-Signal. Wenn eine Session keinen Logeintrag aus Position 4 erzeugt, wurde sie nicht abgeschlossen, und du weißt genau, wo du suchen musst.
  - Was loggen: { session_id, timestamp, agent_id, output_summary, status_written }
Die vier Positionen bilden zusammen einen Trace von der Klassifizierungsentscheidung über den Handoff-Vertrag und den Lesevorgang des Spezialisten bis zur finalen Ausgabe. Jede Lücke in diesem Trace zeigt dir, dass die Session gestartet, aber nicht abgeschlossen wurde, und der letzte Logeintrag vor der Lücke zeigt dir, wo sie gestoppt hat.
[TABLE]
  | Position | Was sie erfasst | Was sie dir sagt, wenn etwas schiefgeht |
  | 1 - Anfrage klassifiziert | Rohe Eingabe, query_type, Session-ID | Ob der Classifier die richtige Entscheidung getroffen hat |
  | 2 - State vor Handoff geschrieben | Vollständiger Handoff-State-Snapshot | Ob der Spezialist die korrekten Eingaben erhalten hat |
  | 3 - State beim Eintritt gelesen | State-Werte, die der Spezialist tatsächlich gelesen hat | Ob der Handoff-Vertrag intakt angekommen ist |
  | 4 - Antwort geschrieben | Ausgabe, Status-Schlüssel, Completion-Signal | Ob die Session abgeschlossen wurde und mit welcher Ausgabe |
## Was nicht geloggt werden sollte
Logging hat Kosten: Speicher, Lesezeit und Datenschutzrisiko. Drei Inhaltskategorien sollten nicht in Logs erscheinen.
- Nutzeridentifizierbare Inhalte. Der rohe Anfragetext enthält oft Namen, Account-Referenzen oder interne Details. Das Feld raw_query an Position 1 ist für Debugging nützlich, sollte in einem Produktionssystem aber nur in einem Log-Kanal mit angemessenen Zugriffskontrollen gespeichert werden und niemals in einem geteilten oder öffentlichen Log-Stream.
- Credentials und Tokens. Jeder Wert, der Zugriff auf ein externes System ermöglicht (API-Schlüssel, Bearer Tokens, Session-Cookies), darf niemals in einem Logeintrag erscheinen. Wenn ein Log-Schritt diese Werte schreibt, wird das Log selbst zu einer Sicherheitslücke.
- Inhalte, die niemals persistieren dürfen. Dieselben Regeln, die Memory Ownership bestimmen (aus Sprint 3), gelten für Logs. Wenn ein Informationselement in der Memory-Architektur als „darf nicht persistieren" identifiziert wurde, sollte es nicht in einem Logeintrag erscheinen. Logs sind Persistenz.
## Verbindung zu deinem Projekt
Die in Sprint 3 definierte Memory- und State-Architektur legt exakt fest, welche Daten gespeichert werden, wo diese abgelegt sind und wer darauf zugreifen darf. Observability ist die logische Erweiterung dieser Spezifikation für den Produktivbetrieb: Sie definiert, wann genau protokolliert wird, was im System geschieht, damit sich das Verhalten der Architektur im Nachhinein lückenlos nachvollziehen lässt.
Bevor die Sprint-4-Integrationsarbeit beginnt, sollten die vier Log-Positionen oben auf deine Projekt-Canvas abgebildet werden. Für jede Position solltest du beantworten können: Welcher Node in meiner Architektur ist dafür verantwortlich, diesen Logeintrag zu schreiben, und welche konkreten Schlüssel loggt er? Wenn eine Position keinen verantwortlichen Node hat, ist sie eine nicht überwachte Lücke im System.
In deinem Projekt besitzt der Classifier (oder Koordinator) Position 1 und 2. Jeder Spezialagent besitzt Position 3. Der finale Reply-Node besitzt Position 4. Die konkreten Details hängen von deinem gewählten Archetyp ab (Router, Coordinator oder Evaluator), aber die vier Positionen gelten in jedem Fall.
## Zusammenfassung
Ein Multi-Agent-System, das im Testing funktioniert, kann in der Produktion unter gleichzeitiger Last scheitern, und die Fehler sind ohne die richtigen Logeinträge schwer zu diagnostizieren. Kontextfenster skalieren sauber, weil sie per Design session-isoliert sind. Flow State skaliert nicht sauber, wenn irgendein Schlüssel global statt pro Session geschrieben wird. Das ist eine Produktionskonsequenz der Memory-Boundary-Entscheidungen aus Sprint 3, kein neues Problem.
Observability über ein Multi-Agent-System hinweg erfordert Logging an vier Positionen: Anfrageklassifizierung, State vor dem Handoff geschrieben, State beim Eintritt des Spezialisten gelesen und Antwort geschrieben. Zusammen bilden diese vier Positionen einen Trace, der die gesamte Ausführungskette abdeckt. Jede Lücke im Trace identifiziert den spezifischen Agenten und Handoff, an dem ein Fehler aufgetreten ist.
In der nächsten Lektion identifizierst du gezielt die Fälle, in denen Memory oder State Fehler verursachen. Du lernst, wie du diese anhand deiner neu generierten Logs erkennst, und entwirfst entsprechende Safeguards, bevor du den neuen Agenten vollständig integrierst.
