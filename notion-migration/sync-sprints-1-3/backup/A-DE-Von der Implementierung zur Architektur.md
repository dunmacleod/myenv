Selin starrte seit zwanzig Minuten auf dieselbe Folie. Die interne Demo von Vela Systems zur Zwei-Agenten-Flowise-Canvas war gut gelaufen. Das Team hatte diese Canvas in Sprint 2 gebaut. Der Commercial-Agent und der Technical-Agent beantworteten beide ihre jeweiligen Anfragen korrekt. Der Condition-Node routete sauber. Jonas war zufrieden gewesen. Doch dann fragte ein Kunde etwas Einfaches: Was passiert, wenn die Agenten mitten in der Konversation Informationen teilen müssen? Selin hatte keine Antwort. Sie schaute auf die Canvas. Ihr wurde klar: Sie wusste nicht, wo die Informationen zwischen den Schritten sich befinden. Sie wusste nicht, wer sie besaß. Sie wusste nicht, was nach dem Ende der Konversation mit ihnen geschah.
Die Agenten funktionierten. Das war nicht dasselbe wie zu verstehen, wie sie sich erinnerten.
In Sprint 2 hast du Memory auf jedem Agent-Node konfiguriert. Du hast allMessages aktiviert, einen Memory-Typ festgelegt und weitergemacht. Das war zu diesem Zeitpunkt der richtige Schritt. Aber Memory in einem Multi-Agent-System ist mehr als eine Node-Einstellung. Es ist eine Architekturentscheidung. Sie bestimmt, was jeder Agent wissen kann. Sie bestimmt, was zwischen Agenten weitergegeben wird. Sie bestimmt, was über Sessions hinweg bestehen bleibt. Und sie bestimmt, was passiert, wenn etwas schiefgeht. Diese Entscheidungen waren im Sprint-2-Build implizit. Sprint 3 macht sie sichtbar.
> 💡 In dieser Lektion lernst du, Memory als architektonisches Thema zu behandeln. Du fragst nicht nur, wie Memory konfiguriert wird. Du fragst auch, was gespeichert wird, wo es lebt und wer darauf zugreifen kann.

## Von Konfiguration zu Entscheidung
Konfigurierst du Memory auf Node-Ebene, beantwortest du eine enge Frage: Hat dieser Agent Memory aktiviert, und welchen Typs? Das ist eine gültige Frage. Sie ist aber nicht die einzige Frage.
Architektonisches Denken stellt drei weitere Fragen, die Node-Konfiguration nicht beantworten kann:
1. Was sollte gespeichert werden? Nicht alles, was durch eine Konversation läuft, ist es wert, erinnert zu werden. Ein Beispiel: Die Anfrage eines Kunden zu einem Lieferantenkoordinationsproblem ist speicherwürdig. Sie formt den Kontext des nächsten Agenten. Anders sieht es beim Klassifizierungslabel aus, das das LLM vergeben hat. Das ist nur dann speicherwürdig, wenn ein nachgelagerter Agent es braucht. Braucht nur der Direct-Reply-Node dieses Label, lohnt sich das Speichern nicht. Auch der rohe Eingabetext aus einem früheren Turn ist ein Grenzfall. Er ist speicherwürdig, wenn der Agent später darauf Bezug nehmen muss. Er ist problematisch, wenn er sensible Daten enthält, die nicht persistieren sollten.
1. Wo befindet es sich? Memory kann an drei Orten liegen. Im Kontextfenster eines einzelnen Agenten. In Flow State, der auf der Canvas geteilt wird. Oder in einem persistenten Store, der über die Session hinaus bestehen bleibt. Jeder Ort hat einen anderen Scope, eine andere Lebensdauer und eine andere Zugänglichkeit. Behandelst du alle drei als austauschbar, entstehen Memory-Bugs. Ein Agent liest dann veraltete Informationen, weil der falsche Store verwendet wurde. Oder zwei Agenten überschreiben sich gegenseitig, weil sie Zustand teilen, den sie eigentlich nicht teilen sollten.
1. Wer kann darauf zugreifen? In einem Multi-Agent-System brauchen verschiedene Agenten oft unterschiedliche Sichten auf die Konversation. Der Commercial-Agent bei Vela könnte die Account-Historie des Kunden brauchen. Der Technical-Agent könnte das Fehlerlog aus der vorherigen Interaktion benötigen. Keiner von beiden braucht die Informationen, die für den jeweils anderen bestimmt sind. Wahrscheinlich sollte auch keiner von beiden Zugriff darauf haben. Zugriff ist eine Designentscheidung, kein Standard.
## Die drei Memory-Orte
Bevor Entscheidungen getroffen werden können, müssen die Orte klar unterschieden werden.
[TABLE]
  | Ort | Was es ist | Lebensdauer | Wer kann es lesen |
  | Agentenkontextfenster | Die Nachrichtenhistorie, die bei der Ausführung dieses Agenten direkt an das Modell übergeben wird | Ein Turn | Nur dieser Agent |
  | Flow State | Key-Value-Paare, die während der Ausführung in $flow.state geschrieben werden | Diese Session | Jeder Node in derselben Canvas |
  | Persistenter Store | Externer Speicher (eine Datenbank, ein Document Store oder ein Vector Store), in den über Sessions hinweg geschrieben und aus dem wieder gelesen wird | Über Sessions hinweg | Jeder Agent mit Zugriffsdaten und einem Retrieval-Schritt |
Diese drei sind nicht austauschbar. Das Kontextfenster verschwindet, wenn der Turn des Agenten endet. Flow State wird geleert, wenn die Session geschlossen wird. Ein persistenter Store bleibt bestehen, bis etwas den Datensatz explizit löscht. Verwendest du Flow State dort, wo eigentlich Persistenz nötig wäre, wird das System schwerer zu verstehen. Dasselbe gilt umgekehrt: Setzt du einen persistenten Store ein, wo nur ein Wert an den nächsten Node übergeben werden muss, entsteht unnötige Komplexität. Beides macht das System schwerer zu reparieren.
In der Sprint-2-Canvas gab es den $flow.state.query_type in Flow State. Das war die richtige Wahl. Es musste nur lange genug bestehen bleiben, damit der Condition-Node es lesen und die Anfrage routen konnte. Es musste nicht über die Session hinaus persistieren. Anders sieht es aus, wenn Vela möchte, dass sich der Commercial-Agent daran erinnert, worüber ein Kunde letzte Woche gefragt hat. Dann wäre Flow State der falsche Ort. Diese Information braucht einen persistenten Store.

## Warum die Unterscheidung in der Praxis zählt
Zwei Probleme treten häufig in Multi-Agent-Systemen auf, wenn diese drei Orte verwechselt werden.
- State Bleed. Ein Agent schreibt an einen Ort, den der falsche Node liest. Ein Beispiel: Der Commercial-Agent schreibt eine detaillierte Kundenzusammenfassung in $flow.state.client_summary. Der Technical-Agent liest diesen Wert, prüft aber nicht, ob er für die aktuelle Anfrage überhaupt relevant ist. Das Ergebnis: Der Technical-Agent übernimmt veraltete oder irrelevante Informationen in seine Antwort. Das Problem ist nicht Memory an sich. Das Problem ist, dass der falsche Agent auf Informationen zugegriffen hat, die er gar nicht lesen sollte.
- Persistenzkonflikt. Ein Agent schreibt Informationen in Flow State und erwartet, dass sie in der nächsten Session noch verfügbar sind. Zum Beispiel eine Kundenpräferenz, eine frühere Lösung oder den Namen eines Nutzers. Die Session endet. Flow State wird geleert. Die nächste Session beginnt frisch. Der Agent verhält sich jetzt so, als hätte er noch nie mit diesem Kunden gesprochen. Die Lösung liegt nicht darin, den Memory-Typ auf Node-Ebene zu ändern. Die Lösung liegt darin, diese Information von Anfang an in einen persistenten Store zu legen.
Beide Probleme lassen sich leichter verhindern als im Nachhinein diagnostizieren. Deshalb ist Memory ein architektonisches Thema. Die Entscheidung über den Ort wird zur Designzeit getroffen, nicht während des Debuggings.
## Die Designfragen vor der Konfiguration
Für das Vela-System schärfen drei Fragen jede Memory-Entscheidung.
1. Muss diese Information die Session überleben? Wenn ein Kunde heute nach Lieferantenkoordination fragt und morgen zurückkommt, sollte sich der Agent an die frühere Konversation erinnern? Wenn ja, reicht Flow State nicht aus. Ein persistenter Store wird benötigt. Ist die Information nur für das Routing dieser Session relevant, ist Flow State korrekt.
1. Welche Agenten brauchen Zugriff? Braucht nur ein Agent ein Informationselement, gehört es in das Kontextfenster dieses Agenten oder in einen Flow-State-Schlüssel, den nur dieser Agent liest. Brauchen mehrere Agenten Zugriff, ist Flow State angemessen. Der Schlüssel sollte dann aber einmal geschrieben und danach nur noch sorgfältig gelesen werden. Er sollte nicht von mehreren Agenten geschrieben und mitten in der Session überschrieben werden.
1. Was darf nicht gespeichert werden? Manche Informationen sollten niemals persistieren. Der rohe emotionale Zustand eines Kunden während einer Beschwerde. Ein temporärer Autorisierungscode. Informationen, die nur für diese eine Interaktion gültig sind, gehören ebenfalls dazu. Sie würden jeden zukünftigen Agenten, der sie liest, in die Irre führen. Zu entscheiden, was nicht persistieren darf, ist genauso wichtig wie zu entscheiden, was persistieren sollte.

Auf diese Fragen gibt es keine pauschalen Antworten, denn sie hängen stark vom Zweck des jeweiligen Systems ab. Entscheidend ist, sie zu klären, bevor die Memory-Funktion konfiguriert wird, und nicht erst, wenn das System bereits unerwartetes Verhalten zeigt. Genau diese vorausschauende Arbeitsweise trainieren wir in diesem Sprint.

## Zusammenfassung
Memory in einem Multi-Agent-System ist kein Node-Schalter. Sie ist eine Reihe von Entscheidungen darüber, was gespeichert wird, wo es gespeichert wird und wer es lesen darf. Die drei Speicherorte (Agentenkontextfenster, Flow State, persistenter Store) unterscheiden sich in Lebensdauer, Scope und Zugänglichkeit. Behandelst du sie als austauschbar, entstehen Bugs. Und diese Bugs sind im Nachhinein schwer zu diagnostizieren.
Diese Lektion markiert einen Shift: von Konfiguration zu Design. Du stellst die Memory-Fragen schon in der Architekturphase, bevor überhaupt etwas gebaut wird. So werden deine Entscheidungen absichtlich statt zufällig. Die nächsten Lektionen schärfen zwei weitere Designthemen: Was passiert, wenn mehrere Agenten gemeinsam Zugriff auf Memory haben? Und welche Informationen sollten überhaupt niemals gespeichert werden?
