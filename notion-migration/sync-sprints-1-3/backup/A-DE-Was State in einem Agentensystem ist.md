# Was State in einem Agentensystem ist

Notion page: https://app.notion.com/p/Was-State-in-einem-Agentensystem-ist-f3a9418319f38294b7ca01d5995d7371
Backed up before n8n migration

Selin hatte es zweimal auf das Whiteboard gezeichnet und hatte trotzdem das Gefühl, dass etwas fehlte. Die Vela-Canvas routete Anfragen korrekt. Der Commercial-Agent beantwortete kommerzielle Anfragen. Der Technical-Agent beantwortete technische. Memory war konfiguriert. Aber als Jonas fragte, was passieren würde, wenn der Hybrid Handler mitten in der Antwort in einen Timeout liefe, hatte Selin keine klare Antwort. Der Agent würde neu starten. Aber würde er wissen, dass er die Anfrage bereits klassifiziert hatte? Würde er wissen, welcher Spezialist aufgerufen worden war? Würde er erneut klassifizieren?
Die Antwort hing von etwas ab, das das Team nicht explizit entworfen hatte: State.
Memory und State sind verwandt, aber verschieden. Memory ist das, was ein Agent aus vergangenen Interaktionen weiß. Zum Beispiel die Konversationshistorie, gespeicherte Präferenzen oder abgerufene Dokumente. State ist, wo das System genau jetzt in seiner aktuellen Ausführung steht: welcher Schritt abgeschlossen ist, was die Zwischenergebnisse sind und worauf der nächste Node wartet. Memory persistiert über Zeit. State verfolgt die Position innerhalb eines einzelnen Runs.
> 💡 In dieser Lektion lernst du, was State ist und wie er sich von Memory unterscheidet. Außerdem siehst du, warum gutes State Management entscheidet, ob sich ein Multi-Agent-System von Unterbrechungen erholt oder still falsche Ausgaben produziert.

## Memory vs. State: der praktische Unterschied
Eine hilfreiche Art, die Unterscheidung zu behalten: Memory beantwortet die Frage „Was weiß dieser Agent?", State beantwortet die Frage „Wo befindet sich diese Ausführung gerade?"
Wenn ein Kunde eine Nachricht an die Vela-Canvas sendet, tritt das System in einen Run ein. Der LLM Classifier wird ausgeführt und schreibt query_type: "technical" in $flow.state. Der Condition-Node liest diesen Wert und routet zum Technical-Agent. Der Technical-Agent beginnt mit der Ausführung. In dem Moment, in dem der Technical-Agent läuft, ist der State des Systems: Klassifizierung abgeschlossen, Routing abgeschlossen, Spezialist antwortet. Das ist keine Memory. Es ist die Live-Position der aktuellen Ausführung.
Memory wäre relevant, wenn der Technical-Agent wissen müsste, wonach dieser Kunde letzte Woche gefragt hatte oder ob sein vorheriges Problem gelöst wurde. Diese Information kommt aus einem persistenten Store oder aus der allMessages-Historie der Session. Sie beschreibt die Vergangenheit. State beschreibt den aktuellen Run.
Beide können interagieren. Memory aus einer früheren Session kann den initialen State des aktuellen Runs beeinflussen. Zum Beispiel, wenn der Account-Status eines wiederkehrenden Kunden zu Beginn einer neuen Session abgerufen und in $flow.state geschrieben wird, bevor das Routing beginnt. Aber sie bleiben unterschiedliche Themen. Memory ohne State Management erzeugt Agenten, die sich an die Vergangenheit erinnern, aber nicht wissen, wo sie in der Gegenwart stehen. State ohne Memory erzeugt Agenten, die isoliert korrekt ausführen, aber nicht auf früheren Interaktionen aufbauen können.
## Woraus State in Flowise besteht
In Flowise Agentflow V2 wird State über Flow State verwaltet: die Key-Value-Paare, die auf dem Start-Node definiert und während der Ausführung von jedem Node über llmUpdateState oder gleichwertige Mechanismen aktualisiert werden.
Flow State hat drei Eigenschaften, die ihn zum richtigen Container für Ausführungs-State machen:
- Er ist über die Canvas hinweg geteilt. Jeder Node im selben Agentflow kann aus $flow.state lesen und hineinschreiben. Genau das macht ihn für die Koordination zwischen Agenten nützlich. Der Condition-Node liest $flow.state.query_type, weil der LLM Classifier es dort geschrieben hat. Ohne eine geteilte Oberfläche wäre jeder Node isoliert.
- Er ist session-scoped. Flow State wird initialisiert, wenn eine Session startet, und geleert, wenn sie endet. Er persistiert nicht in die nächste Session. Dadurch eignet er sich dafür, die Position der aktuellen Ausführung zu verfolgen, ohne veraltete Werte aus früheren Runs anzusammeln.
- Er ist strukturiert. Flow-State-Schlüssel haben deklarierte Typen. Ein Schlüssel, der als String geschrieben wird, kann nicht versehentlich als Zahl gelesen werden. Diese Struktur reduziert die Klasse von Bugs, die entstehen, wenn ein Agent einen Wert in einem Format schreibt, das der nächste Agent nicht erwartet.
Was Flow State nicht tut: Er verfolgt die Ausführungshistorie nicht automatisch. Er speichert den aktuellen Wert jedes Schlüssels, nicht die Sequenz von Werten, die dieser Schlüssel hatte. Wenn der Classifier query_type: "technical" schreibt und ein Retry ihn anschließend mit query_type: "commercial" überschreibt, enthält Flow State den neuesten Wert. Er zeichnet nicht auf, dass die erste Klassifizierung stattgefunden hat. Für Ausführungshistorie wird zusätzliches Logging oder ein externer Store benötigt.
## Warum State Management in Multi-Step-Systemen zählt
In einem Single-Agent-, Single-Turn-System ist State trivial. Der Agent erhält Eingabe, erzeugt Ausgabe, und der Run ist abgeschlossen. Es gibt keine Position zu verfolgen. Sobald ein System jedoch mehrere Schritte, mehrere Agenten oder die Möglichkeit einer Unterbrechung hat, wird State zu einer Koordinationsoberfläche.
Drei Fehlermodi entstehen, wenn State nicht explizit verwaltet wird.
- Doppelte Ausführung: Ein Run wird unterbrochen, nachdem der Classifier ausgeführt wurde, aber bevor das Ergebnis in den Flow State geschrieben werden konnte. Führt das System nun einen Retry aus, läuft der Classifier einfach noch einmal durch. Abhängig von der Modelltemperatur und der genauen Eingabe erzeugt er beim zweiten Mal womöglich eine völlig andere Klassifizierung. Das führt dazu, dass das System dieselbe Anfrage innerhalb derselben Session plötzlich an einen anderen Spezialisten weiterleitet. Zudem fehlt jeglicher Nachweis darüber, dass die erste Klassifizierung jemals stattgefunden hat.
- Veraltetes Routing. $flow.state.query_type wird zu Beginn einer Session gesetzt. Kommt eine zweite Anfrage in derselben Session an und der Schlüssel wird weder geleert noch aktualisiert, kann die zweite Anfrage anhand der ersten Klassifizierung geroutet werden. Der Kunde stellte zuerst eine kommerzielle Frage und wurde zum Commercial-Agent geroutet. Dann stellte er eine technische Frage und landete trotzdem wieder beim Commercial-Agent, weil der State-Schlüssel noch "commercial" enthielt.
- Unsichtbare Teilerledigung. Ein Multi-Step-Run schließt die ersten drei Schritte ab und scheitert beim vierten. State erfasst hier nur den aktuellen Schritt, nicht die bereits abgeschlossenen. Beim Retry weiß das System deshalb nicht, dass Schritt eins bis drei schon erfolgreich liefen. Es startet von vorne und wiederholt Arbeit, die eigentlich schon korrekt erledigt war. Am Ende bekommt der Kunde eine doppelte oder widersprüchliche Antwort.
Alle drei Fehlermodi haben dieselbe Ursache: Das System wusste am Fehlerpunkt nicht, wo es sich in der Ausführung befand. Explizites State Management verhindert das. Also bewusst zu entscheiden, was aufgezeichnet wird, wann es aufgezeichnet wird und wie es bei der Wiederherstellung genutzt wird.

## State in der Vela-Canvas
Die Sprint-2-Canvas verwaltet State über drei Flow-State-Schlüssel: query_type, confidence und client_query. Jeder wird vom LLM Classifier geschrieben und vom Condition-Node und den Spezialagenten gelesen.
Das ist ein sinnvoller Ausgangspunkt. Aber es lässt einige State-Entscheidungen offen.
Die Schlüssel werden zwischen Anfragen in derselben Session nicht zurückgesetzt. Wenn ein Kunde zwei Nachrichten in derselben Session sendet (zuerst eine kommerzielle Anfrage, dann eine technische), enthält query_type nach der zweiten Klassifizierung "technical", was korrekt ist. Aber nur, weil der Classifier erneut läuft und den Wert überschreibt. Wenn der Classifier beim zweiten Run scheitern würde und das System auf den zwischengespeicherten Wert zurückfiele, würde die zweite Anfrage mit der Klassifizierung der ersten Anfrage geroutet. Die Canvas hat derzeit keinen Mechanismus, um das zu erkennen oder zu verhindern.
Completion wird nicht aufgezeichnet. Sobald der Spezialagent antwortet und der Direct-Reply-Node feuert, ist der Run abgeschlossen. Aber es gibt keinen status-Schlüssel in Flow State, der erfasst, ob der Run erfolgreich abgeschlossen wurde. Wenn ein externes System prüfen müsste, ob die Kundenanfrage bearbeitet wurde, hätte es kein state-basiertes Signal zum Lesen.
Ungenutzter Confidence-Schlüssel: Der Schlüssel confidence wird zwar geschrieben, aber nicht genutzt. Der Classifier speichert einen Confidence-Wert unter $flow.state.confidence, doch kein Element auf der Canvas greift darauf zu. Dieser State existiert somit im System, hat jedoch keinen Consumer. Das ist nicht zwingend problematisch. Möglicherweise ist das Feld bereits für eine zukünftige Routing-Regel reserviert. Dennoch sollte dies eine bewusste Designentscheidung sein und kein bloßes Versehen.
Das sind keine Bugs. Es sind Designlücken, die relevant werden, wenn das System Unterbrechungen, Retries oder Multi-Turn-Sessions mit state-abhängigem Routing behandeln muss. Die Sprint-3-Projektabgabe verlangt von dir, die State-Architektur für dein eigenes System zu definieren. Die Vela-Canvas ist das Übungsfeld, um zu erkennen, was diese Definition abdecken muss.
## Zusammenfassung
 State beschreibt den aktuellen Status einer laufenden Ausführung. Er definiert, welche Prozesse abgeschlossen sind, wie die Zwischenergebnisse lauten und worauf der nächste Schritt wartet. Das unterscheidet ihm vom Memory, das festhält, was ein Agent aus vergangenen Interaktionen gelernt hat. Beide Konzepte arbeiten eng zusammen. Werden sie jedoch verwechselt, entstehen Systeme, die sich zwar korrekt an die Vergangenheit erinnern, aber den aktuellen Run völlig aus den Augen verlieren.
Flow State in Flowise: In Flowise ist der Flow State die zentrale Komponente für den Zustand. Er wird über die gesamte Canvas hinweg geteilt, ist klar strukturiert und an die jeweilige Session gebunden. Dieser State füllt sich allerdings nicht von selbst. Was genau wann und durch welchen Node in den Flow State geschrieben wird, sind bewusste Designentscheidungen. Bleiben diese unklar, führt das unweigerlich zu den zuvor beschriebenen Fehlern. Aus diesem Grund müssen diese Festlegungen von Beginn an explizit getroffen werden.
Ausblick auf die Praxis: Die nächste Lektion überträgt diese Theorie in die konkrete Implementierung. Wir entwerfen ein State-Handoff-Muster, bei dem ein Agent seine Ergebnisse sowie die Kontrolle über einen strukturierten Schreibvorgang im Flow State nahtlos an den nächsten Agenten übergibt.
