Selin had drawn it on the whiteboard twice and still felt like something was missing. The Vela canvas routed queries correctly. The Commercial Agent answered commercial queries. The Technical Agent answered technical ones. Memory was configured. But when Jonas asked what would happen if the Hybrid Handler timed out mid-response, Selin didn't have a clean answer. The agent would restart. But would it know it had already classified the query? Would it know which specialist had been called? Would it try to classify again?
The answer depended on something the team hadn't designed explicitly: State.
Memory and state are related but distinct. Memory is what an agent knows from past interactions such as the conversation history, the stored preferences, the retrieved documents. State is where the system is right now in its current execution, which step has completed, what the intermediate results are, and what the next node is waiting for. Memory persists across time. State tracks position within a single run.
> 💡 In this lesson, you will learn what state is, how it differs from memory, and why managing it correctly determines whether a multi-agent system can recover from interruptions or silently produce wrong output.

## Memory vs state: The practical difference
A useful way to hold the distinction: memory answers the question "what does this agent know?", state answers the question "where is this execution right now?"
When a client sends a message to the Vela canvas, the system enters a run. The LLM Classifier executes and writes query_type: "technical" to $flow.state. The Condition node reads that value and routes to the Technical Agent. The Technical Agent begins executing. At the moment the Technical Agent is running, the state of the system is: classification complete, routing complete, specialist responding. That is not memory. It is the live position of the current execution.
Memory would be relevant if the Technical Agent needed to know what this client had asked about last week, or whether their previous issue was resolved. That information comes from a persistent store or the session's allMessages history. It describes the past. State describes the present run.
The two can interact. A previous session's memory might influence the current run's initial state. For example, if a returning client's account status is retrieved at the start of a new session and written to $flow.state before routing begins. But they remain distinct concerns. Memory without state management produces agents that remember the past but don't know where they are in the present. State without memory produces agents that execute correctly in isolation but can't build on prior interactions.

## What state consists of in Flowise
In Flowise Agentflow V2, state is managed through Flow State: the key-value pairs defined on the Start Node and updated by any node during execution via llmUpdateState or equivalent mechanisms.
Flow State has three properties that make it the right container for execution state:
- It is shared across the canvas. Every node in the same agentflow can read from and write to $flow.state. This is what makes it useful for coordination between agents. The Condition node reads $flow.state.query_type because the LLM Classifier wrote it there. Without a shared surface, each node would be isolated.
- It is session-scoped. Flow State is initialised when a session starts and cleared when it ends. It does not persist to the next session. This makes it appropriate for tracking the position of the current execution without accumulating stale values from previous runs.
- It is structured. Flow State keys have declared types. A key written as a string cannot be accidentally read as a number. This structure reduces the class of bugs that come from one agent writing a value in a format the next agent doesn't expect.
What Flow State does not do is track execution history automatically. It stores the current value of each key, not the sequence of values it has held. If the Classifier writes query_type: "technical" and then a retry overwrites it with query_type: "commercial", Flow State holds the most recent value. It does not record that the first classification happened. For execution history, additional logging or an external store is needed.

## Why state management matters in multi-step systems
In a single-agent, single-turn system, state is trivial. The agent receives input, produces output, and the run is complete. There is no position to track. But as soon as a system has multiple steps, multiple agents, or the possibility of interruption, state becomes a coordination surface.
Three failure modes appear when state is not managed explicitly.
- Duplicate execution. If a run is interrupted after the Classifier has executed but before the result is written to Flow State, and the system retries from the beginning, the Classifier runs again. Depending on the model's temperature and the input phrasing, it might produce a different classification the second time. The system now routes to a different specialist — for the same query, in the same session — without any record that the first classification happened.
- Stale routing. If $flow.state.query_type is set at the start of a session and not cleared or updated when a second query arrives in the same session, the second query might be routed based on the first query's classification. The client asked a commercial question, got routed to the Commercial Agent, then asked a technical question and was routed to the Commercial Agent again because the state key still held "commercial".
- Invisible partial completion. A multi-step run completes the first three steps and fails on the fourth. If state only records the current step and not the completed steps, the system on retry has no way to know that steps one through three succeeded. It restarts from the beginning, repeats work that was already done correctly, and the client receives a duplicated or contradictory response.
All three failure modes share a common root: the system did not know where it was in the execution at the point of failure. Explicit state management (deciding what to record, when to record it, and how to use it during recovery) is what prevents them.

## State in the Vela canvas
The Sprint 2 canvas manages state through three Flow State keys: query_type, confidence, and client_query. Each is written by the LLM Classifier and read by the Condition node and the specialist agents.
That is a reasonable starting point. But it leaves some state decisions unresolved.
The keys are not reset between queries in the same session. If a client sends two messages in the same session (first a commercial query, then a technical one), query_type will hold "technical" after the second classification, which is correct. But only because the Classifier runs again and overwrites the value. If the Classifier failed on the second run and the system fell back to the cached value, the second query would be routed using the first query's classification. The canvas currently has no mechanism to detect or prevent this.
Completion is not recorded. Once the specialist agent responds and the Direct Reply node fires, the run is complete. But there is no status key in Flow State that records whether the run completed successfully. If an external system needed to verify that the client's query was handled, it would have no state-based signal to read.
The confidence key is written but not acted on. The Classifier writes a confidence value to $flow.state.confidence, but nothing in the canvas reads it. It is state that exists in the system but has no consumer. That is not necessarily wrong. It may be a field reserved for a future routing rule, but it should be a deliberate decision, not an oversight.
These are not bugs. They are design gaps that become relevant when the system needs to handle interruptions, retries, or multi-turn sessions with state-dependent routing. Sprint 3's project deliverable asks you to define the state architecture for your own system. The Vela canvas is the practice ground for identifying what that definition needs to cover.

## Summary
State is the position of an execution in progress; what has completed, what the intermediate results are, and what the next step is waiting for. It is distinct from memory, which tracks what an agent knows from past interactions. The two interact, but confusing them produces systems that remember the past correctly and lose track of the present run.
In Flowise, Flow State is the primary state surface: shared across the canvas, session-scoped, and structured. It is not automatic. What gets written to Flow State, when, and by which node are all design decisions. The failure modes that appear when those decisions are left unclear are the motivation for making them explicit.
