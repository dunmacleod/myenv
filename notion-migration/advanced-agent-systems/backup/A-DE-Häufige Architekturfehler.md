# Häufige Architekturfehler

Notion page: https://app.notion.com/p/H-ufige-Architekturfehler-bbe9418319f38300879f0159bd050711
Backed up before n8n migration

Selin überprüft die erste Version von Velas Agent (die in der Produktion ausfiel) mit frischem Blick. Die Fehlermodi aus der Einstiegslektion dieses Sprints lassen sich jetzt leichter benennen: inkonsistente Routing-Antworten, verschlechterte Leistung unter Last, eine Änderung von zwanzig Minuten, die einen ganzen Tag dauerte. Damals diagnostizierte das Team diese Probleme als Bugs. Sie wurden einzeln gepatcht. Die Patches führten zu neuen Problemen.
Was Selin jetzt sieht: Jeder Fehler ließ sich auf einen konkreten Architekturfehler zurückführen, der gemacht wurde, bevor ein einziger Node zur Canvas hinzugefügt wurde. Die Fehler sahen nicht wie Fehler aus, als sie gemacht wurden. Sie sahen wie vernünftige Abkürzungen aus: ein schneller Weg, die Canvas früher zum Laufen zu bringen, eine Konfiguration, die harmlos wirkte, eine Designentscheidung, die sich zu diesem Zeitpunkt flexibel anfühlte.
> 💡 Diese Lektion benennt die drei Fehler, die in echten Agentensystemen am häufigsten auftreten, erklärt, warum sie schwer zu erkennen sind, bevor sie Schaden verursachen, und zeigt, wie man jeden davon früh genug erkennt, um ihn auf Designebene statt auf Patch-Ebene zu beheben.

## Fehler 1: Over-Engineering
- Was es ist: mehr Nodes, mehr Agenten, mehr Routing-Logik und mehr Koordinationsaufwand hinzufügen, als das Problem tatsächlich erfordert.
- Warum es passiert: Komplexität fühlt sich wie Gründlichkeit an. Eine Canvas mit einem Supervisor-Node, drei spezialisierten Workern, einem Loop-Node und vier Branches für Flow-State-Handling sieht leistungsfähiger aus als ein einzelner Agent-Node mit einem klaren System-Prompt. Sie ist leistungsfähiger für ein Problem, das dieses Maß an Koordination benötigt. Für ein Problem, das es nicht benötigt, sind die zusätzlichen Nodes eine Belastung.
Over-Engineering zeigt sich in zwei Formen. Die erste ist vorzeitiger Multi-Agent: ein einzelner Agent wird in zwei oder mehr Agenten aufgeteilt, bevor es Belege dafür gibt, dass ein Agent die Aufgabe nicht erfüllen kann. Die zweite ist unnötiges Branching: Condition-Nodes und Routing-Pfade für Szenarien hinzufügen, die noch nicht aufgetreten sind, unter der Annahme, dass sie irgendwann auftreten werden.
Beide Formen haben dieselben Kosten: Mehr Nodes bedeuten mehr Stellen, an denen die Ausführung scheitern kann, mehr Flow-State-Schlüssel, die verwaltet werden müssen, mehr Tool-Beschreibungen, die sich nicht überschneiden dürfen, und mehr Stellen zum Debuggen, wenn tatsächlich etwas schiefgeht.
- Das Vela-Beispiel: Die erste Version von Velas Agent hatte implizite Routing-Logik innerhalb eines einzelnen Agent-Node, der zu viele Dinge erledigen sollte. Der vorgeschlagene Fix von Jonas' Kollegen war, mehrere spezialisierte Agenten hinzuzufügen. Das wäre Over-Engineering gewesen. Das eigentliche Problem war, dass der eine Agent nicht bewusst entworfen worden war. Ein gut abgegrenzter Single-Agent mit einem klaren System-Prompt bearbeitet Velas drei Anfragetypen zuverlässiger und mit weniger Overhead als drei spezialisierte Agenten mit einem Supervisor, der zwischen ihnen routet.
- Das Signal, auf das Sie achten sollten: Wenn die Begründung für einen weiteren Agenten lautet „das könnte später nützlich sein" oder „es fühlt sich robuster an", ist das Over-Engineering. Die Begründung für einen weiteren Agenten sollte ein konkreter, beobachtbarer Fehler im bestehenden Agenten sein, den der neue Agent beheben soll.
### Fehler 2: Versteckter Zustand
- Was es ist: Flow State auf eine Weise verwenden, die nicht deklariert, dokumentiert oder vorhersehbar ist: in einen Schlüssel schreiben, der nie initialisiert wurde, einen Schlüssel lesen, dessen Wert von einem Pfad abhängt, den die aktuelle Ausführung möglicherweise nicht genommen hat, oder Zustand über eine Session hinweg ansammeln lassen, sodass spätere Anfragen beeinflusst werden.
- Warum es passiert: Flow State ist praktisch. Jeder Node kann an jedem Punkt der Ausführung in jeden Schlüssel schreiben. Diese Flexibilität macht es einfach, Daten zwischen nicht benachbarten Nodes weiterzugeben, ohne explizite Verbindungen hinzuzufügen. Sie macht es aber auch einfach, Zustand einzuführen, den niemand entworfen hat und den niemand vollständig versteht.
Versteckter Zustand hat drei häufige Formen:
1. Nicht deklarierte Schlüssel: Ein Node schreibt in $flow.state.approval_result, ohne dass dieser Schlüssel im Start-Node initialisiert wurde. Der Schlüssel existiert und der Schreibvorgang gelingt, aber es gibt keinen expliziten Nachweis, dass der Schlüssel Teil der Architektur ist. Wenn ein anderer Node später versucht, $flow.state.approval_result auf einem Pfad zu lesen, auf dem der schreibende Node nie ausgeführt wurde, erhält er einen undefinierten Wert. Der nachgelagerte Node verhält sich unerwartet, und die Ursache ist im Ausführungs-Trace nicht offensichtlich.
1. Pfadabhängige Werte: Ein Schlüssel wird auf einem Branch eines Condition-Node geschrieben, aber nicht auf dem anderen. Ein nachgelagerter Node, der den Schlüssel auf beiden Branches liest, verhält sich auf dem Branch korrekt, auf dem der Schreibvorgang stattgefunden hat, und auf dem Branch falsch, auf dem er nicht stattgefunden hat, aber nur unter den spezifischen Eingabebedingungen, die den unbeschriebenen Branch auslösen. Diese Fehlerklasse ist im Testing leicht zu übersehen und schwer zu reproduzieren.
1. Session-Akkumulation: Memory, das mit allMessages und ohne Window-Limit konfiguriert ist, behält jede Gesprächsrunde einer langen Session. Der Agent-Node fügt diese vollständige Historie in jeden neuen Prompt ein. Nach zwanzig Gesprächsrunden über drei verschiedene Themen enthält das Kontextfenster irrelevante frühere Turns, die die Interpretation neuer Anfragen durch den Agenten verzerren. Der Agent denkt technisch korrekt, nur eben auf Basis eines Kontexts, der längst nicht mehr passt.
- Das Vela-Beispiel: Die Baseline-Canvas hat zwei vorab deklarierte, aber leere Flow-State-Schlüssel: query_type und status_response. Diese existieren genau, um versteckten Zustand zu verhindern: Die Schlüssel sind im Start-Node sichtbar, ihr Zweck ist benannt, und jeder Node, der in sie schreibt, schreibt in eine bekannte, deklarierte Struktur. Schlüssel auf Node-Ebene hinzuzufügen, ohne sie im Start-Node zu deklarieren, ist der Fehler, den dieses Designmuster verhindert.
- Das Signal, auf das Sie achten sollten: Wenn ein Flow-State-Schlüssel in der Konfiguration eines Nodes erscheint, aber nicht in der Initialisierungsliste des Start-Node, ist er versteckter Zustand. Prüfen Sie den Start-Node gegen jede $flow.stateReferenz auf der Canvas, bevor die Architektur als vollständig betrachtet wird.
### Fehler 3: Fragile Handoffs
- Was es ist: eine Verbindung zwischen zwei Nodes oder zwei Agenten so entwerfen, dass angenommen wird, die Ausgabe eines Nodes komme in einem bestimmten Format an, ohne zu behandeln, was passiert, wenn sie das nicht tut.
- Warum es passiert: Beim Bau einer Canvas ist es naheliegend, zuerst den Happy Path zu testen. Agent A erzeugt eine gut strukturierte Antwort. Agent B liest sie und nutzt sie korrekt. Die Verbindung funktioniert. Das Problem ist, dass das Ausgabeformat von Agent A nicht garantiert ist. Es ist das Ergebnis einer Modellinferenz, und Modellinferenz ist nicht deterministisch. Unter leicht anderen Eingabebedingungen kann derselbe Agent-Node eine Antwort mit einem fehlenden Feld, einem anderen Schlüsselnamen oder einem Format erzeugen, das ein nachgelagerter Node nicht parsen kann.
Fragile Handoffs zeigen sich in drei konkreten Formen:
1. Formatabhängigkeit: Ein Condition-Node erwartet, dass $flow.state.next einen von drei bestimmten String-Werten enthält ("worker_a", "worker_b", "done"). Der Supervisor-LLM-Node wird per Prompt angewiesen, einen dieser drei Werte zu schreiben. Bei den meisten Eingaben tut er das. Bei manchen Eingaben, etwa mehrdeutigen Anfragen, sehr kurzen Eingaben oder Eingaben in einer unerwarteten Sprache, schreibt er "Worker A" oder "complete" oder gar nichts. Der Condition-Node hat keinen passenden Branch, und die Ausführung scheitert still.
1. Fehlender Fallback: Ein Agent-Node ist auf dem Erfolgspfad mit einem Direct-Reply-Node verbunden. Es gibt keinen Pfad dafür, was passiert, wenn der Agent-Node eine leere Antwort oder einen Fehler erzeugt. Die Ausführung erreicht eine Sackgasse, kein Direct Reply feuert, die Unterhaltung stoppt, und der Nutzer erhält nichts.
1. Enge Kopplung: Die Ausgabe von Agent A wird direkt als System-Prompt-Kontext für Agent B verwendet, ohne Transformationsschritt dazwischen. Wenn sich die Ausgabe von Agent A in Länge, Struktur oder Ton verändert, verschiebt sich das Verhalten von Agent B unvorhersehbar, weil sich sein Kontext verschoben hat. Die beiden Agenten sind gekoppelt, ohne eine definierte Schnittstelle zwischen ihnen.
- Das Vela-Beispiel: Eine frühere Vela-Canvas verwendete einen Loop-Node mit einem Max Loop Count von 2 und einem Fallback-Direct-Reply auf dem Branch „retries exhausted". Das war ein bewusstes Handoff-Design. Die Schleife hatte eine definierte Abbruchbedingung, und der Ausstiegspfad hatte eine definierte Antwort. Das ist der richtige Ansatz. Eine Canvas, in der der Loop-Node keinen Max Loop Count hat oder der Branch für ausgeschöpfte Wiederholungsversuche ins Leere führt, ist ein fragiler Handoff, der nur darauf wartet zu scheitern.
- Das Signal, auf das Sie achten sollten: Fragen Sie für jede Node-Verbindung auf der Canvas: Was passiert, wenn der vorgelagerte Node eine unerwartete Ausgabe erzeugt? Wenn die Antwort lautet „die Canvas hat dafür keinen Pfad", ist der Handoff fragil.

## Wie die drei Fehler mit den drei Pfeilern zusammenhängen
Jeder Fehler ist ein Versagen in einem der drei Architekturpfeiler aus der vorherigen Lektion:
[TABLE]
  | Fehler | Ursprungspfeiler | Beobachtbares Symptom |
  | Over-Engineering | Orchestrierung | Die Canvas ist schwerer zu debuggen, als das Problem rechtfertigt; Koordinations-Nodes erhöhen die Latenz, ohne die Zuverlässigkeit zu erhöhen |
  | Versteckter Zustand | Zustandsverwaltung | Unerwartetes Agentenverhalten, das je nach Ausführungspfad variiert; Context Bleed über Themen hinweg; nicht deklarierte Schlüssel erzeugen undefinierte Lesezugriffe |
  | Fragile Handoffs | Kommunikation | Die Ausführung stoppt still; nachgelagerter Node verhält sich bei bestimmten Eingaben unerwartet; kein Fallback-Pfad feuert |
Diese Zuordnung ist wichtig, weil der Fix für jeden Fehler in demselben Pfeiler liegt wie der Fehler selbst. Over-Engineering wird korrigiert, indem die Orchestrierung vereinfacht wird: Nodes fliegen raus, die sich ihren Platz nicht verdient haben. Versteckter Zustand wird korrigiert, indem die Zustandsverwaltung geprüft wird: jeder Schlüssel muss deklariert sein, und jeder Schreibvorgang muss auf jedem Ausführungspfad stattfinden, von dem nachgelagerte Nodes später lesen. Fragile Handoffs werden korrigiert, indem die Kommunikation bewusst gestaltet wird: durch explizite Formatbeschränkungen, Fallback-Pfade und Transformationsschritte zwischen eng gekoppelten Nodes.
Zu wissen, zu welchem Pfeiler ein Fehler gehört, zeigt direkt, wo der Fix vorgenommen werden sollte.

### Zusammenfassung
Drei Fehler, drei Ursprungspfeiler, drei Frühwarnsignale. Over-Engineering fügt Koordinationsaufwand hinzu, den das Problem nicht rechtfertigt. Das Signal ist eine Canvas, die schwerer zu debuggen ist, als das Problem erfordert. Versteckter Zustand erzeugt Schlüssel und Memory, die nicht Teil der deklarierten Architektur sind. Das Signal ist ein Flow-State-Schlüssel, der in einem Node erscheint, aber nicht im Start-Node. Fragile Handoffs nehmen Ausgabeformate an, die nicht garantiert sind; das Signal ist eine Node-Verbindung ohne Pfad für unerwartete Eingaben.
Der Sprint-1-Walkthrough in der nächsten Lektion baut ein Single-Agent-System für Vela, bei dem alle drei Fehler bewusst vermieden werden: Die Orchestrierung ist nicht komplexer, als das Problem erfordert, jeder Flow-State-Schlüssel ist im Start-Node deklariert, und jede Verbindung hat einen definierten Pfad für den Fall, dass der vorgelagerte Node eine unerwartete Ausgabe erzeugt. So sieht ein bewusst entworfener Agent aus, bevor er getestet wird.
