# Warum die Architektur für Agents wichtig ist

Notion page: https://app.notion.com/p/Warum-die-Architektur-f-r-Agents-wichtig-ist-b099418319f3839582b701f20bebe947
Backed up before n8n migration

Vela Systems hat einen funktionierenden Agenten. Selin, die Produktmanagerin, die die AI-Praxis leitet, hat ihn gemeinsam mit Jonas und Petra innerhalb von zwei Wochen erstellt: eine einzelne Agentflow-V2-Canvas mit einem Start Node, einem Agent Node und einem Direct Reply Node. Er kann Gespräche führen, Fragen zu Inventar und Fulfillment beantworten und innerhalb seines definierten Anwendungsbereichs bleiben. Während der internen Tests bewältigte er jede Anfrage, die das Team ihm stellte.
Dann stellten sie ihn dem gesamten Operations-Team zur Verfügung.
Innerhalb von drei Tagen begann der Agent, auf dieselbe Frage unterschiedliche Antworten zu geben, je nachdem, wie sie formuliert war. Während einer arbeitsreichen Phase wurden die Antwortzeiten immer länger, und schließlich reagierte er auf einige Anfragen überhaupt nicht mehr. Als Jonas eine Funktion zur Kommunikation mit Lieferanten hinzufügen wollte, stellte er fest, dass die erforderliche Änderung denselben Bereich der Canvas betraf wie die Speicherkonfiguration. Eine Anpassung des einen beschädigte das andere.
Nichts stürzte ab. Es gab keine Fehlermeldung. Der Agent wurde einfach auf eine Weise unzuverlässig, die sich nur schwer nachvollziehen, beheben und dem restlichen Team erklären ließ. Das Problem war die Architektur.

> 💡 Am Ende dieser Lektion wirst du verstehen, warum die Entscheidungen beim Entwurf eines Agenten darüber bestimmen, ob er auch mit zunehmender Komplexität zuverlässig bleibt.

## Was Architektur tatsächlich bedeutet
Architektur ist nicht dasselbe wie Konfiguration. Konfiguration sind die Einstellungen, die du auf einzelne Nodes anwendest: welches Modell verwendet wird, was im System Prompt steht oder wie viele Nachrichten im Speicher behalten werden. Architektur sind die Entscheidungen, die festlegen, wie diese Nodes zueinander in Beziehung stehen: wie Daten zwischen ihnen fließen, welcher Node für welche Informationen verantwortlich ist und was passiert, wenn etwas schiefgeht.
Wenn ein Agent klein ist (ein Node, der eine Aufgabe erfüllt), spielt Architektur kaum eine Rolle. Die Canvas ist die Architektur und sie ist so einfach, dass du sie vollständig im Kopf behalten kannst. Doch sobald ein Agent wächst, werden früh getroffene Architekturentscheidungen tragend. Ändere eine Sache, und an anderer Stelle verschiebt sich unerwartet etwas.
Velas Agent wuchs ohne einen Architekturplan. Die Speicherkonfiguration war mit der Routing-Logik verflochten. Der System Prompt übernahm Aufgaben, die in separate Nodes gehört hätten. Es gab keinen definierten Ablauf für Fehlerfälle. Der Agent funktionierte, bis er unter realen Bedingungen, von echten Nutzern und in realem Umfang eingesetzt wurde. Erst dann wurden die Lücken sichtbar.
## Die drei Dinge, die Architektur bestimmt
Jede Agentenarchitektur trifft Entscheidungen in drei Dimensionen. Jede davon führte bei Vela zu einem konkreten Problem.
Zuverlässigkeit beschreibt, ob der Agent das tut, was er tun soll: konsistent und für alle Eingaben, die er in der Praxis tatsächlich erhält. Velas Agent gab auf umformulierte Anfragen unterschiedliche Antworten, weil die Routing-Logik implizit in einem einzigen, überladenen Agent Node verborgen war. Es gab keinen expliziten Pfad für unterschiedliche Anfragetypen. Das Modell leitete das Routing aus dem Kontext ab, je nach Formulierung unterschiedlich.
Skalierbarkeit beschreibt, ob der Agent auch bei steigendem Volumen, wachsender Komplexität oder erweitertem Umfang zuverlässig funktioniert. Als Velas Operations-Team den Agenten gleichzeitig nutzte, verschlechterten sich die Antwortzeiten und einige Anfragen wurden gar nicht mehr beantwortet. Die Architektur bot keine Möglichkeit, Anfragen mit hoher Priorität von Routineanfragen zu trennen. Alles lief durch denselben Node, auf dieselbe Weise und mit derselben Verarbeitungsgeschwindigkeit.
Wartbarkeit beschreibt, ob sich der Agent verändern lässt (z. B. durch das Hinzufügen einer Funktion, das Beheben eines Verhaltens oder das Aktualisieren eines Prompts), ohne an anderer Stelle unbeabsichtigte Folgen zu verursachen. Jonas stellte fest, dass die Canvas zu einem einzigen Kopplungspunkt geworden war: Die Speicherkonfiguration und die Routing-Logik befanden sich im selben Node, sodass Änderungen an einem Bereich ein Verständnis des anderen erforderten. Eine Änderung, die zwanzig Minuten hätte dauern sollen, beanspruchte fast einen ganzen Tag und führte zusätzlich zu einem neuen Problem.

## Warum das wichtig ist, bevor du mit dem Erstellen beginnst
Die meisten Probleme, die bei Agenten erst während der Nutzung sichtbar werden, wurden bereits in der Entwurfsphase entschieden. Sobald ein Agent in den Händen echter Nutzer ist, sind die Architekturentscheidungen fest in der Canvas verankert. Sie zu ändern bedeutet, die Canvas grundlegend umzubauen.
Genau darin liegt der Unterschied zwischen dem Beheben eines Zuverlässigkeitsproblems und der Neuarchitektur eines Agenten. Ein Zuverlässigkeitsproblem zu beheben bedeutet, einen Prompt oder eine Retrieval-Einstellung anzupassen. Eine Neuarchitektur bedeutet dagegen, die Beziehungen zwischen den Nodes, den Zustandsfluss und die Verantwortlichkeiten neu zu gestalten. Das ist ein deutlich größerer Aufwand, und fast immer geschieht er unter Zeitdruck, weil der Agent zu diesem Zeitpunkt bereits produktiv genutzt wird.
Das Ziel dieses Moduls ist, dir beizubringen, Agenten zuerst zu entwerfen: also die Entscheidungen zu treffen, die Zuverlässigkeit, Skalierbarkeit und Wartbarkeit bestimmen, bevor sie in einer Canvas festgeschrieben werden, die sich später nur noch schwer ändern lässt.
Velas Agent mit seinen drei Nodes fehlt eine durchdachte Architektur. Die nächsten Lektionen stellen die Werkzeuge vor, mit denen er richtig entworfen werden kann.
## Zusammenfassung
Velas Agent funktionierte in den Tests und scheiterte im produktiven Einsatz, weil niemand ausdrücklich entschieden hatte, wie die Architektur mit realen Nutzungsszenarien umgehen sollte. Die drei Probleme, die das Team erlebte, ließen sich jeweils auf eine andere Dimension zurückführen: inkonsistente Antworten entstanden durch eine Lücke bei der Zuverlässigkeit, langsame Antworten durch mangelnde Skalierbarkeit und ein ganzer Arbeitstag für eine zwanzigminütige Änderung durch fehlende Wartbarkeit.
