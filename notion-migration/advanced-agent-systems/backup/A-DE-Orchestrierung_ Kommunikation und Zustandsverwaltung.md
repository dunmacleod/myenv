# Orchestrierung, Kommunikation und Zustandsverwaltung

Notion page: https://app.notion.com/p/Orchestrierung-Kommunikation-und-Zustandsverwaltung-6e99418319f3828caf8181e573554cdb
Backed up before n8n migration

Selin hat das Muster bestätigt: ein gut entworfenes Single-Agent-System. Vela braucht in dieser Phase nicht mehrere Agenten. Aber als Jonas beginnt, die neue Canvas zu skizzieren, merkt er, dass „Single-Agent“ immer noch viele Entscheidungen offenlässt. Welcher Node steuert, wann der Agent-Node ausgeführt wird? Wie gelangt die Ausgabe des Agenten an die richtige Stelle? Was passiert mit dem Kontext, der von einem Schritt zum nächsten weitergetragen werden muss?
Das sind Designfragen, keine Konfigurationsfragen. Sie tauchen in jedem Agentensystem auf, egal ob es einen Agenten hat oder zehn. Drei Aspekte liegen jedem Architekturmuster zugrunde: Orchestrierung, Kommunikation und Zustandsverwaltung. Alle drei richtig zu gestalten, macht den Unterschied zwischen einem Agenten, der in einer Demo funktioniert, und einem, der in der Produktion standhält.
> 💡 In dieser Lektion lernt ihr, was Orchestrierung, Kommunikation und Zustandsverwaltung jeweils bedeuten und warum ihre Vermischung eine der häufigsten Ursachen für Agentenfehler ist. 

## Orchestrierung
Orchestrierung ist der Mechanismus, der steuert, wann welcher Teil des Workflows ausgeführt wird und in welcher Reihenfolge.
In Agentflow V2 ist die Orchestrierung explizit: Die visuellen Verbindungen zwischen Nodes auf der Canvas definieren den Ausführungspfad. Der Start-Node löst den Agent-Node aus, der eine Ausgabe erzeugt, die zum Direct-Reply-Node fließt. Nichts wird ausgeführt, wenn nicht ein verbundener Node davor abgeschlossen wurde. Es werden keine Annahmen getroffen.
Das ist wichtig, weil Orchestrierung der Ort ist, an dem Entscheidungen zu Reihenfolge, Branches und Schleifen liegen. Ein Condition-Node, der zu einem von drei nachgelagerten Agent-Nodes routet, ist eine Orchestrierungsentscheidung. Ein Loop-Node, der die Ausgabe eines Workers zurück an den Supervisor sendet, ist eine Orchestrierungsentscheidung. Ein Iteration-Node, der jedes Element in einer Liste verarbeitet, bevor es weitergeht, ist eine Orchestrierungsentscheidung.
Der Fehlermodus, wenn Orchestrierung nicht bewusst entworfen wird: Nodes werden in einer Reihenfolge ausgeführt, die unerwartete Ergebnisse erzeugt. Oder Schleifen feuern ohne definierte Abbruchbedingung. Oder ein Branch, der Fehler behandeln sollte, hat keinen Pfad. Das sind keine Bugs in einem Node, das sind Lücken in der Orchestrierung.
Velas aktuelle Baseline hat die einfachste mögliche Orchestrierung: Start → Agent → Direct Reply. Ein Pfad, keine Branches, keine Schleifen. Für ein Single-Agent-System, das einheitliche Anfragen bearbeitet, reicht das. Die Orchestrierung wird komplexer, sobald die Canvas unterschiedliche Anfragetypen bearbeiten oder mehrere Schritte koordinieren muss.
# Kommunikation
Kommunikation beschreibt, wie Daten zwischen Nodes bewegt werden, was ein Node an den nächsten übergibt und in welcher Form.
In Agentflow V2 läuft die Kommunikation auf zwei Wegen. Der erste ist die direkte Ausgabereferenz: Ein nachgelagerter Node liest die Ausgabe eines bestimmten vorherigen Nodes mit nodeName.output . Das ist Point-to-Point. Die Verbindung ist explizit, und die Daten fließen automatisch darüber.
Der zweite Weg ist der Flow State: ein zur Laufzeit geteilter Key-Value-Store über alle Nodes innerhalb einer einzelnen Ausführung hinweg, in den jeder Node mit $flow.state.keyName lesen oder schreiben kann. Der Flow State ist keine Nachricht, die zwischen zwei Nodes übergeben wird. Es ist ein geteilter Kontext, auf den jeder Node im Flow zugreifen kann, egal ob er direkt mit dem Node verbunden ist, der ihn geschrieben hat.
Der Unterschied ist wichtig, weil die beiden Mechanismen unterschiedliche Probleme lösen:
[TABLE]
  |  | Direkte Ausgabereferenz | Flow State |
  | Verwenden, wenn | Die Ausgabe eines Nodes die direkte Eingabe für den nächsten ist | Daten für nicht benachbarte Nodes oder über Branches hinweg verfügbar sein müssen |
  | Beispiel | Ausgabe des Agent-Node → Nachricht im Direct Reply | Supervisor schreibt next in $flow.state; Condition-Node liest es auf der anderen Seite eines Branches |
  | Scope | Zwischen zwei verbundenen Nodes | Über die gesamte Ausführung hinweg |
  | Persistenz | Nicht gespeichert, wird durch die Verbindung weitergegeben | Für die Dauer der Ausführung im Memory gespeichert, wird zwischen Durchläufen zurückgesetzt |
Der Fehlermodus, wenn Kommunikation nicht bewusst entworfen wird: Ein Node kann nicht auf benötigte Daten zugreifen, weil sie über eine Route übergeben wurden, mit der er nicht verbunden ist. Oder Flow-State-Schlüssel werden geschrieben, ohne im Start-Node deklariert zu sein. Oder ein nachgelagerter Node liest einen Schlüssel, der nie aktualisiert wurde.
Die Baseline von Vela verwendet ausschließlich direkte Ausgabereferenzen. Der Output des Agent-Nodes fließt direkt in den Direct-Reply-Node. Ein Flow-State ist zwar vorhanden, wird aber aktuell noch nicht beschrieben. Das ist so gewollt, um die Baseline minimal zu halten. Sobald der Canvas komplexer wird, rückt die Kommunikation als Designaspekt stärker in den Fokus.
## Zustandsverwaltung
Zustandsverwaltung ist die Disziplin zu entscheiden, welche Informationen bestehen bleiben, wo sie liegen, wer darauf zugreifen kann und was passiert, wenn ein Schritt fehlschlägt.
Zustand und Kommunikation hängen zusammen, sind aber nicht dasselbe. Kommunikation dreht sich darum, Daten von einem Node zu einem anderen zu bewegen. Zustandsverwaltung dreht sich um die Lebensdauer und Ownership dieser Daten: ob sie über Gesprächsrunden hinweg bestehen bleiben, welche Agenten sie lesen dürfen und wie eine sichere Wiederherstellung aussieht, wenn mitten in der Ausführung etwas schiefgeht.
In Agentflow V2 existiert Zustand auf zwei Ebenen:
1. Conversation Memory: Was der Agent über Gesprächsrunden hinweg in einer Session erinnert. Konfiguriert am Agent-Node oder LLM-Node mit Einstellungen für Memory-Typ, Window Size und Token-Limit. Das ist das Memory, das es einem Nutzer erlaubt zu sagen: „Was ist mit der zweiten Option?", und der Agent versteht, was gemeint ist. Es bleibt über Gesprächsrunden hinweg bestehen, ist aber auf einen Conversation Thread beschränkt.
1. Flow State ($flow.state): Was Nodes innerhalb einer einzelnen Ausführung teilen. Initialisiert im Start-Node. Zu Beginn jeder neuen Ausführung zurückgesetzt. Nicht über separate Unterhaltungen hinweg sichtbar. Das ist Laufzeitzustand, der Scratchpad für einen Durchlauf des Flows.
Der Fehlermodus, wenn Zustandsverwaltung nicht bewusst entworfen wird: Ein Agent trägt Kontext von einem Thema in ein anderes (Context Bleed). Ein Node schreibt in einen Flow-State-Schlüssel, der nie deklariert wurde. Ein fehlgeschlagener Schritt hinterlässt einen veralteten Wert in $flow.state, der das Reasoning eines nachgelagerten Nodes beschädigt. Oder Memory wächst über eine lange Session hinweg und verschlechtert Routing-Entscheidungen.
Velas Baseline hat Memory mit allMessages als Memory-Typ aktiviert. Das heißt, jede Gesprächsrunde in der Session wird behalten und in jeden späteren Prompt eingefügt. Für eine kurze Session mit einem fokussierten Thema ist das in Ordnung. Für eine längere Session mit mehreren nicht zusammenhängenden Anfragen wird es zum Zuverlässigkeitsrisiko. Genau diese Art von Context Bleed trat in der ersten Version von Velas Agent auf.
Zustandsverwaltung ist der Aspekt, der mit wachsender Agentenkomplexität am schnellsten skaliert. Ein Single-Agent-System mit einer Memory-Konfiguration und zwei leeren Flow-State-Schlüsseln hat relativ wenig zu verwalten. Ein Multi-Agent-System mit mehreren Agenten, die manche Zustandsinformationen teilen und andere nicht, mit Handoffs, die strukturierten Kontext weitertragen, hat sehr viel zu verwalten. Sprint 3 dieses Moduls widmet sich vollständig diesem Thema.
## Warum alle drei gemeinsam entworfen werden müssen
Orchestrierung, Kommunikation und Zustandsverwaltung sind nicht unabhängig voneinander. Eine Änderung an einem Aspekt beeinflusst die anderen.
![image]((notion-hosted file))
Wenn die Orchestrierung einen neuen Branch hinzufügt, muss das Kommunikationsdesign sicherstellen, dass die auf diesem Branch benötigten Daten verfügbar sind, entweder über eine direkte Verbindung oder über Flow State. Wenn Kommunikation auf Flow State beruht, muss das Design der Zustandsverwaltung sicherstellen, dass diese Schlüssel deklariert, korrekt initialisiert und sauber behandelt werden, falls ein Node sie nicht schreibt. Wenn die Zustandsverwaltung eine neue Memory-Grenze zwischen Agenten einführt, muss die Orchestrierung definieren, welchen Pfad jeder Agent nimmt, damit die Grenze eingehalten wird.
Deshalb entwickeln Agenten, die Node für Node gebaut werden, ohne ein Design, das alle drei Aspekte berücksichtigt, tendenziell Lücken, die erst bei Skalierung oder unter echten Nutzungsbedingungen sichtbar werden. Velas erster Agent hatte implizite Orchestrierung (ein Pfad, keine Branches, keine definierte Fehlerbehandlung), implizite Kommunikation (kein Flow-State-Design, nur eine direkte Ausgabereferenz) und implizite Zustandsverwaltung (Memory standardmäßig aktiviert, keine Regeln dazu, was behalten oder gelöscht werden soll). Er funktionierte, bis er es nicht mehr tat.
Das Architektur-Briefing, das Sie am Ende dieses Sprints erstellen (und das Projekt-Briefing, das Sie in Ihren Live-Sessions entwickeln), wird alle drei Aspekte für den Agenten dokumentieren, den Sie entwerfen. Nicht als akademische Übung, sondern weil ein Briefing, das das Orchestrierungsmuster, den Kommunikationsmechanismus und die Zustandsgrenzen benennt, eine Canvas beschreibt, die gebaut, getestet und ohne Erklärung an jemand anderen übergeben werden kann.
## Zusammenfassung
Jede Agentenarchitektur trifft Entscheidungen über drei Aspekte hinweg: Orchestrierung steuert, wann Dinge ausgeführt werden, Kommunikation steuert, wie Daten bewegt werden, und Zustandsverwaltung steuert, was bestehen bleibt und wie lange. Die drei hängen voneinander ab. Eine Lücke in einem Aspekt zeigt sich meist als Fehler in einem der anderen.
Velas Baseline hat alle drei, aber in ihrer einfachsten Form: lineare Orchestrierung, Kommunikation über direkte Ausgabe und standardmäßiger Memory-Zustand. Die nächsten Lektionen arbeiten darauf hin, diese Entscheidungen bewusst statt standardmäßig zu treffen und zu wissen, wie jede einzelne begründet werden kann. Das Entscheidungsframework in der nächsten Lektion ist das Werkzeug dafür.
